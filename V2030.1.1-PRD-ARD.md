# open-ontologies v2030.1.1 — PRD / ARD

**Repository:** `seanchatmangpt/open-ontologies`  
**Ecosystem role:** public-ontology  
**Release:** Chatman Ecosystem v2030.1.1  
**Standing conferred by this document:** `UNKNOWN` — requirements are not execution evidence.

## Product requirement

`open-ontologies` SHALL be the public semantic memory of the Chatman Ecosystem. It SHALL provide vendor-neutral, machine-readable concepts from which cloud, marketplace, process, security, economic, identity, authority, evidence, and software-manufacturing projections can be derived without making a proprietary schema the canonical truth.

The product objective is **one admitted meaning, many projections**. A new provider, marketplace, protocol, or runtime SHOULD normally extend mappings and constraints rather than force a new canonical business model.

## Required capabilities

1. Prefer public vocabularies including RDF/RDFS/OWL, SHACL, SKOS, PROV-O, DCAT/DCTERMS, ODRL, ORG, QUDT, SOSA/SSN, FIBO, and OCEL where semantically applicable.
2. Define Chatman-specific vocabulary only for irreducible gaps, with explicit equivalence/subclass/mapping relationships where lawful.
3. Represent `Observation`, `AdmittedObservation`, `Capability`, `Constraint`, `Authority`, `Actuation`, `Receipt`, `Replay`, `Standing`, `Marketplace`, `Entitlement`, `Deployment`, `Process`, `Cost`, `Risk`, and `Falsifier` as first-class semantic coordinates.
4. Preserve `UNKNOWN != ADMITTED`, `UNSUPPORTED != REFUSED`, and simulation/inspection/execution as distinct states.
5. Provide shapes/constraints sufficient for consumers to fail closed on malformed or semantically incomplete graphs.
6. Version ontology identities and migrations so downstream projections can declare exact semantic compatibility.
7. Preserve provenance for imported standards, generated alignments, and local extensions.

## Architecture requirements

Canonical flow:

```text
public standards + observed provider vocabularies
        -> alignment graph
        -> admission/shapes
        -> canonical ontology capsule
        -> consumer queries / ggen projections
```

The repository SHALL NOT become an actuation system. Ontology assertions, inference results, LLM output, or generated mappings have no ambient DO authority.

The graph SHALL support DfCM: model capability alternatives before vendor selection, preserve reversible lawful mappings, and expose exclusions rather than collapsing absent mappings into generic failure.

## Interfaces

The authoritative surface SHALL be consumable through stable RDF serializations and SPARQL-compatible queries. Machine-readable validation artifacts SHALL be available for downstream `ggen`, `gymact`, `autofde`, marketplace, and formal-admission consumers.

## Acceptance for v2030.1.1

A release candidate is admissible only if:

- canonical graphs parse deterministically;
- required SHACL/admission gates pass;
- public-ontology alignments are provenance-bound;
- representative cloud and marketplace concepts can map to canonical capabilities without vendor ownership of the canonical model;
- negative fixtures reject unknown/invalid closed-vocabulary transitions where required;
- a deterministic graph fingerprint can be recomputed;
- downstream consumers can pin an exact ontology version/hash.

`ALIVE` requires execution of the exact admitted ontology subject through its owning verifier. This document alone is never that evidence.

## Falsifiers

The v2030.1.1 ontology architecture is falsified if a required ecosystem capability can only be represented by making one vendor's schema canonical; if generated mappings cannot be traced to source semantics; or if two supposedly equivalent provider mappings produce materially different canonical meaning without an explicit distinction.

## Ecosystem contract

`open-ontologies` is upstream semantic authority. It supplies meaning; it does not manufacture runtime authority. Consumers MAY project it, but MUST preserve provenance, admission, authority boundaries, and claim ceilings.
